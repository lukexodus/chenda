Core Algorithms

The two building
blocks of everything.

Algorithm 01
Haversine Distance
// O(1) — great circle distance
INPUT
buyer_lat, buyer_lng
product_lat, product_lng
IF
same location → RETURN 0
Convert coords to radians
delta_lat = product_lat − buyer_lat
delta_lng = product_lng − buyer_lng
a = sin²(Δlat/2) +
cos(b_lat) · cos(p_lat) · sin²(Δlng/2)
c = 2 · atan2(√a, √(1−a))
RETURN
EARTH_RADIUS_KM × c
Algorithm 02
Shelf-Life Metrics
// O(1) — four derived metrics
INPUT
total_shelf_life_days
days_already_used
listed_date, current_date
remaining = total − days_used
freshness% = (remaining / total) × 100
expiry = listed_date + remaining
IF
current_date > expiry
is_expired = TRUE
ELSE
is_expired = FALSE
RETURN
remaining, freshness%, expiry, is_expired
Practical Notes

Clean theory.
Real-world caveats.

⚠
USDA Transformer — Double Pass
usda-transformer.js rebuilds each USDA record into an object more than once. Asymptotically O(p·f), but worth consolidating for large catalogs.
⚠
Seller Analytics — Multiple Passes
SellerAnalytics.tsx performs several separate passes over the same product list. Technically O(a + u log u) but has a higher constant factor than needed.
○
SQL / PostGIS Layer — Out of Scope
Exact bounds for ST_DWithin, ST_Distance, GiST/GIN index use, and materialized-view refresh cannot be reliably derived from the JS codebase alone. Depends on PostgreSQL planner decisions at runtime.
✓
Pipeline is Cleanly Composed
The standalone chenda_algorithm.js package has identical asymptotics to the production backend. The architecture scales gracefully — no hidden quadratic traps in the core path.

Linear
by design.

The CHENDA pipeline is architecturally efficient. Every step is O(n) until ranking — and that's by necessity, not negligence.
